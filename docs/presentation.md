# 스마일 디자인 이미지 생성 — 개발 경과 (세미나용)

PPT 11장 기준 초안. 슬라이드마다 **핵심 메시지 1줄 + 근거 3~4개 + 이미지 1장**으로 구성했다.
삽입용 이미지는 `docs/presentation_assets/` 에 슬라이드 번호로 정리해 두었다.

---

## 1. 표지 / 한 줄 요약

**환자 사진 한 장으로 치료 후 모습을 2초 만에 보여 준다.**

- 치아 미백·정렬, 웃는 정도, 고개 방향을 조절
- 인터넷 연결 없이 **사내 PC(RTX 4090)에서 직접 구동**
- 상업적 이용이 가능한 공개 모델만 사용

---

## 2. 무엇을 만들었나

> 이미지: `p03_demo_teeth.jpg`

- 입력은 환자 사진 1장. 결과는 같은 크기의 사진
- 미백만 / 정렬만 / 둘 다 등 **원하는 정도를 단계로 선택**
- 입 주변만 새로 그리고 **나머지 픽셀은 원본 그대로** 유지 → 다른 사람처럼 보이지 않는다
- 장당 약 2초

---

## 3. 왜 직접 돌려야 했나 — 모델 선택

**환자 사진을 외부로 보내지 않으려면 사내에서 돌려야 하고, 그러려면 라이선스와 용량 두 가지를 동시에 만족해야 한다.**

| 모델 | 라이선스 | 사내 구동 |
| --- | --- | --- |
| **FLUX.2 klein 4B** | **Apache 2.0 — 상업적 이용 가능** | **가능 (채택)** |
| FLUX.2 klein 9B | 비상업 라이선스 | 상업적 이용은 API 필요 |
| FLUX.2 dev | 비상업 라이선스 | 상업적 이용 불가 |
| FLUX.2 pro | API 전용 (가중치 비공개) | 불가 |

- 상업적으로 쓸 수 있는 건 **4B 하나뿐**이라 선택지가 사실상 정해져 있었다
- 더 큰 모델이 품질은 좋지만, 쓰려면 외부 API로 환자 사진을 보내야 한다
- 참고: 비상업 라이선스의 "결과물 상업 이용" 해석에 이견이 있어, 실제 적용 전 원문 확인 필요

---

## 4. 과제 — 모델이 PC에 안 들어간다

**AI 모델은 세 덩어리로 되어 있고, 그대로 올리면 그래픽카드 메모리가 부족하다.**

| 덩어리 | 역할 | 용량(16비트 기준) |
| --- | --- | --- |
| 텍스트 이해부 | 지시문("치아를 희게")을 숫자로 바꿈 | 7.5GB |
| **이미지 생성부** | 실제로 그림을 그림 | **7.8GB** |
| 이미지 변환부 | 결과를 사진으로 출력 | 0.2GB |
| 합계 | | **약 15.5GB** |

- 여기에 **그리는 동안 쓰는 작업 공간**이 추가로 필요하다 → 실측 피크 **13.5GB**
- RTX 4090의 메모리는 24GB. 빠듯하게 들어가지만 여유가 없다
- 목표: **안정적으로 돌아갈 여유 확보 + 더 낮은 사양에서도 가능하게**

---

## 5. 최적화 ① — 텍스트 이해부를 통째로 들어냈다

**우리가 쓰는 지시문은 미리 정해져 있다. 매번 해석할 필요가 없다.**

- "치아를 희게", "치열을 가지런히" 같은 문장은 **종류가 한정**되어 있다
- 그래서 **미리 한 번만 해석해서 결과를 저장**해 두고, 서비스할 때는 저장된 것을 꺼내 쓴다
- 서버에는 텍스트 이해부를 아예 올리지 않는다

| 효과 | |
| --- | --- |
| 메모리 절약 | **약 8GB** (전체의 절반) |
| 속도 | 매 요청마다 하던 문장 해석이 사라져 더 빠름 |
| 비용 | 문장을 바꾸면 미리 만드는 작업을 다시 해야 함 (약 20초) |

> 비유: 자주 쓰는 문장을 매번 번역하지 않고, 번역본을 미리 만들어 두는 것

---

## 6. 최적화 ② — 숫자 정밀도를 낮췄다

**모델은 숫자 덩어리다. 숫자 하나를 몇 비트로 저장하느냐로 용량이 정해진다.**

| 정밀도 | 이미지 생성부 용량 | 비고 |
| --- | --- | --- |
| 32비트 | 약 15.5GB | 원래 학습 형식 |
| 16비트 | 7.8GB | 절반 |
| **8비트** | **약 3.9GB** | **4분의 1 (채택)** |

실측 (RTX 4090, 1메가픽셀 이미지):

| 설정 | 작업 중 최대 메모리 | 생성 시간 |
| --- | --- | --- |
| 16비트 | 13.5GB | 2.20초 |
| 8비트 저장 | **10.3GB** | 2.28초 |
| 8비트 연산 | 11.1GB | 2.17초 |
| **8비트 연산 + 컴파일** | **9.6GB** | **1.46초** |

- **품질 저하는 눈으로 확인되지 않았다.** 용량만 줄었다
- 8비트 연산 + 컴파일은 **더 빠르면서 메모리도 가장 적다** (16비트 대비 34% 빠름, 3.9GB 절약)
- 단, 컴파일은 서버 시작 후 첫 요청에 수십 초가 걸린다 → 현재 배포는 **8비트 저장**을 기본으로 사용

**결과: 13.5GB → 9.6~10.3GB.** 24GB 그래픽카드에 여유 있게 들어간다.

---

## 7. 최적화 ③ — 모델 자체를 줄이는 시도 (미채택)

> 이미지: `p07_distillation.jpg` (위: 원본 4B 모델 / 아래: 축소한 1B 모델)

**큰 모델의 실력을 작은 모델에 가르치는 방법(증류)을 시도했다.**

- 4B 모델 → **1B 모델**로 축소 학습 (텍스트→이미지, 이미지 편집 각각)
- 결과: **그럴듯한 그림은 나오지만 원본 모델만큼은 아니다**
  - 위 이미지에서 아래 줄(축소 모델)이 디테일·구도에서 밀린다
- 한계
  - 학습에 **시간이 매우 오래** 걸리고, 학습용 이미지도 직접 만들어야 했다
  - 공개 데이터셋은 지시문 품질이 낮아 오히려 학습을 방해했다
  - 품질을 정량적으로 평가할 지표가 아직 없다

**판단: 배포에 쓸 수준이 아니라고 보고 보류.** ⑤⑥번 최적화만으로 목표 사양을 맞췄으므로 우선순위를 낮췄다.

## 8. 무엇을 조절할 수 있나

> 이미지: `p08_features_teeth.jpg` (치아), `p08_features_pose.jpg` (고개), `p08_features_smile.jpg` (웃는 정도)

| 항목 | 단계 | 상태 |
| --- | --- | --- |
| 치아 미백 | 0 / 50 / 100 | 완료 |
| 치아 정렬 | 0 / 50 / 100 | 완료 |
| **미백 + 정렬 조합** | 권장: 정렬 100 + 미백 75 | **완료 (권장)** |
| 고개 방향 | 좌우 / 상하 | 완료 (25·75가 자연스러움) |
| 웃는 정도 | 입 다묾 / 미소 / 윗니 / 윗니+아랫니 | **일부만 동작 (개선 중)** |
| 치아 템플릿 이미지 참조 | — | 효과가 없어 미사용 |

- **미백만으로는 부족한 경우가 많다.** 틈이 있거나 깨진 치아는 **정렬을 같이 걸어야** 고쳐진다

## 9. 어떻게 적용하는 게 가장 좋은가

**바꾸는 범위가 좁을수록 "그 사람 그대로" 남는다. 그래서 치아는 입 주변만 고치고, 항상 마지막에 한다.**

| 바꾸는 것 | 다시 그리는 범위 | 같은 사람으로 보이는 정도 |
| --- | --- | --- |
| **치아 (미백·정렬)** | **입 주변만** | **0.89~0.95** |
| 웃는 정도 | 얼굴 아래 절반 | 0.50~0.74 |
| 고개 방향 | 머리 전체 + 배경 | 0.56~0.88 |

> 1.0이 완전히 같은 사람. 참고로 치아 편집은 눈·코·이마가 **원본 사진 픽셀 그대로**다.

**권장 적용 순서**

```
① (필요할 때만) 고개 방향 바꾸기   ← 전체를 다시 그림
② (필요할 때만) 웃는 정도 바꾸기   ← 얼굴 아래쪽을 다시 그림
③ 치아 미백·정렬                 ← 입 주변만, 항상 마지막
```

- **치아를 마지막에 두는 이유**: 앞 단계가 전체를 다시 그리면서 먼저 고친 치아를 되돌린다 (실측으로 확인)
- **한 번에 섞으면 안 된다**: 웃음과 치아를 한 번에 처리하면 **치아 품질이 크게 떨어진다**
- **기본 제품 기능은 "치아만"**: 1회 처리로 가장 좋은 치아 결과 + 가장 높은 신원 유지
- 고개·웃음은 변화가 커서 **"참고용 시뮬레이션"** 수준으로 본다

## 10. 얼마나 검증했나

> 이미지: `p09_validation_results.jpg` (변경 전/후), `p09_validation_faces.jpg` (테스트용 얼굴 모음)

- 실제 환자 샘플이 **28장**뿐이라, **AI로 다양한 얼굴 112장을 직접 만들어** 테스트했다
  - 치아 상태 14종(누런 치아, 앞니 결손, 깨진 치아, 덧니, 착색 등) × 인종·나이 20종
- 결과: 치아 상태와 관계없이 고르게 희고 가지런한 치아로 바뀜

| 지표 (112장 평균) | 변경 전 | 변경 후 |
| --- | --- | --- |
| 치아 밝기 | 77.7 | 84.8 |
| 치아 누런 정도 (낮을수록 좋음) | 14.3 | 0.8 |
| 같은 사람으로 인식되는 정도 | — | 0.92 (1.0이 동일인) |

- **한계: 112장은 AI가 만든 얼굴**이다. 실제 환자 사진·무표정 얼굴로 추가 검증이 필요하다

## 11. 현황과 다음 단계

> 이미지: `p10_hard_case.jpg` (가장 어려운 케이스 — 금속 보철 + 앞니 결손)

**현황**

- 사내 서버에서 동작하는 상태. 앱에서 바로 연동 가능 (가이드 문서 작성 완료)
- 장당 약 2초, 그래픽카드 메모리 10GB 수준
- 클라우드(AWS) 배포 구성도 준비됨 — 모델과 이미지는 외부로 나가지 않도록 분리

**남은 과제**

1. **실제 환자 사진으로 재검증** — 현재 검증은 합성 이미지 위주
2. **웃는 정도 개선** — "윗니만 보이게"가 아직 잘 동작하지 않음
3. **금속 보철 처리** — 완전히 지워지지 않음
4. 여러 항목을 한 번에 조절할 때의 정확도 개선 (내부 구조 개선안 도출 완료)
