# Smile Design 최종 결과 보고

환자 얼굴 사진 한 장을 받아 **치아 미백·정렬**과 **고개 방향(pose)** 을 편집하는 서버의 최종 구성과 결과를 정리한다.
세부 실험과 수치는 각 절에 링크한 상세 문서에 있다.

## 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 모델 | FLUX.2 Klein 4B (step-distilled, 4 step), transformer fp8 가중치 저장 + bf16 연산 |
| 최종 스타일 | `my/configs/smile_design/smile_final.yaml` (임베딩 라이브러리 `ac177319…`) |
| 편집 항목 | 치아 미백 0~100, 치아 정렬 0~100, 고개 좌우(yaw)·상하(pitch) 0~100 (50 = 원본 유지) |
| 속도 | RTX 4090 기준 장당 약 1.7초 (모델 로드 후). 영역 2개 순차 편집은 약 3.2초 |
| 입력 / 출력 | 환자 사진 1장 → 같은 크기의 PNG. 텍스트 입력 없이 preset 이름이나 control 값만 보낸다 |
| 서버 | `my/design_tune_server.py` (REST API, 브라우저 테스트용 Swagger `/docs`) |

**권장 사용법**

| 목적 | 요청 방식 |
| --- | --- |
| 미백·정렬 | `mode: preset` (`align_whiten` 등) 또는 `grid align_color` + **입 영역 inpaint 마스크** (`regions: ["mouth"], dilate 16, feather 12`) |
| 고개 방향 | `preset` (`turn_left` 등) 또는 `grid yaw_pitch`, **마스크 없음** (`mask: false`) |
| 고개 방향 + 치아 | `mode: delta`로 한 번에 (예: `head_yaw 100 + alignment 100 + tooth_color 75`), 마스크 없음 |
| 치아 템플릿 이미지 | **권장하지 않음** (4절) |

## 1. 치아 미백·정렬

샘플 사진(`my/samples/medit/image.png`, 앞니 결손 + 누런 치아)에 단독 스타일과 조합을 적용했다. 입 영역만 다시 그리므로 얼굴의 나머지는 원본 픽셀 그대로다.

![치아 스타일 비교 (입 확대)](assets/teeth_styles_mouth.jpg)
![치아 스타일 비교 (얼굴 전체)](assets/teeth_styles_full.jpg)

| 구분 | 스타일 | 결과 |
| --- | --- | --- |
| 단독 | 미백 50 / 100 | 50은 색만 밝아지고 결손 틈은 남는다. 100은 매우 희고 틈까지 메워진다 |
| 단독 | 정렬 50 / 100 | 50은 거의 변화 없음. 100은 틈이 메워지고 가지런해지며 약간 밝아진다 |
| 조합 | 정렬 50 + 미백 50 (grid) | 자연스러운 흰색, 틈 메워짐 |
| 조합 | **정렬 100 + 미백 75 (`align_whiten`)** | 고른 치열 + 밝은 흰색. **권장 조합** |
| 조합 | 정렬 100 + 미백 100 (grid) | 가장 밝은 미용 치아 느낌 |
| 조합 | 정렬 → 미백 순차 inpaint 2단계 | 지나치게 희고 푸른빛. 비권장 |
| 조합 | 정렬+미백 한 문장 inpaint | 가장 자연스러운 색조 |

- 결손·파손이 있는 환자에서는 "미백만", "정렬만"도 서로 영향을 준다(미백 100이 틈을 메우고, 정렬 100이 색을 밝힌다).
- `natural`(변화 없음)이 이 사진에서는 앞니에 갈색 얼룩을 만들었다. 원본을 그대로 돌려줘야 하는 경우에는 추론하지 않고 원본을 쓰는 편이 안전하다.

## 2. 고개 방향 (pose)

고개 방향은 머리 전체를 다시 그려야 하므로 마스크 없이 적용한다. 배경·머리카락도 조금씩 바뀐다.

![원본에 pose 적용](assets/pose_on_original.jpg)

- 좌우 회전, 위·아래 보기 모두 의도한 방향으로 뚜렷하게 바뀐다.
- **극단값(0, 100)은 변화가 너무 크다.** 위를 보는 100은 과하고, 아래를 보는 0은 입이 닫혀 치아가 보이지 않는다. **25 / 75가 자연스럽다.**
- 3행처럼 `delta`로 pose와 치아를 한 요청에서 같이 바꾸면 회전과 미백·정렬이 모두 적용된다.

### 2.1 미백·정렬한 결과에 pose를 다시 적용하면

정렬 100 + 미백 100 결과 이미지를 입력으로 pose만 적용했다.

![치아 편집 후 pose](assets/pose_after_teeth.jpg)

- pose 문장에는 "치아 색 유지"가 들어 있어서 이미 하얗게 만든 치아를 대체로 유지한다. 하지만 일부(`natural`, yaw 75)는 원래의 누런 치아로 돌아갔다.
- **권장 순서는 "고개 → 치아"다.** 치아를 먼저 고치면 고개 단계에서 다시 그려져 효과가 절반쯤 사라진다
  (어려운 케이스 실측: b\* 2.6 → 5.0, 반대 순서는 0.2). [sample17_report.md](sample17_report.md) 2장 참고.
  한 번에 처리해야 한다면 `delta`가 아니라 **조합 문장 preset**을 쓴다([embedding_modes.md](embedding_modes.md)).

## 3. 다양한 얼굴에서의 검증

샘플 1장만으로는 일반화가 어려워, FLUX.2 Klein 4B로 치아 상태가 나쁜 합성 얼굴 112장과 치아 템플릿 20장을 만들어 실험했다.
치아 상태 14종(노란 치아, 앞니 결손, 깨진 치아, 덧니, 벌어진 앞니, 착색, 반대교합 등) × 인종·나이 20종이다.

![합성 얼굴 112장](assets/smile_v3_faces.jpg)

아래는 실험용 스타일 `smile_final_smile_v3.yaml`의 `smile_upper_align_whiten`(정렬 100 + 미백 75 + 웃는 정도 75, 아래 얼굴 inpaint)
결과다. 정렬·미백 문장은 최종 스타일과 같다. 원본 → 2열(프롬프트 결과)을 보면 치아 상태와 관계없이 고르게 하얀 치아로 바뀐다.
3~5열은 4.2절의 템플릿 비교다.

![112명 중 12명 결과](assets/smile_v3_template.jpg)

| 지표 (112명 평균) | 원본 | 정렬 100 + 미백 75 (+ 웃는 정도 75) |
| --- | --- | --- |
| 치아 밝기 L* | 77.7 | 84.8 |
| 치아 노란기 b* (클수록 노랗다) | 14.3 | 0.8 |
| 신원 유사도 (ArcFace) | - | 0.92 |

## 4. 추가 실험: 웃는 정도와 치아 템플릿

상세: [docs/smile_tune/smile_template_report.md](../smile_tune/smile_template_report.md)

### 4.1 웃는 정도 (치아 노출) — 실험 단계

실험용 스타일 `smile_final_smile_v3.yaml`에 "치아가 얼마나 보이는지" control을 추가했다. 최종 스타일에는 아직 넣지 않았다.

![웃는 정도 비교](assets/smile_v3_exposure.jpg)

| 값 | 의도 | 112명 결과 |
| --- | --- | --- |
| 0 | 입 다문 무표정 | **100% 동작** (치아가 사라짐). 다만 아래 얼굴을 다시 그려 신원 유사도 0.71 |
| 75 | 윗니만 보이게 | 아랫니가 보이던 얼굴의 19%만 가려짐 → **아직 쓸 수 없음** |
| 100 | 윗니+아랫니 보이게 | 윗니만 보이던 얼굴의 42~45%에서 아랫니가 드러남 → **절반 정도 동작** |

"윗니만 보이는 미소"처럼 결과 상태를 묘사하는 문장은 효과가 없었고, "턱을 벌리고 아랫입술을 내려라"처럼 동작을 지시해야 반응했다.

### 4.2 치아 템플릿 이미지 — 권장하지 않음

이상적인 치아 클로즈업 사진(템플릿)을 두 번째 이미지로 함께 넣는 방식(`patient_tooth`)을 비교했다.

![템플릿 + 프롬프트 (웃는 정도 100)](assets/smile_v3_full_combo.jpg)

| 비교 | 결과 |
| --- | --- |
| 템플릿만 (문장 없이) | 미백·정렬 효과는 프롬프트와 비슷하다 (노란기 b* 3.3 vs 프롬프트 0.8) |
| 템플릿의 치아 "모양"이 옮겨 가는가 | 근거 약함. 템플릿을 더해 생긴 차이(14.9)가 seed만 바꾼 차이(13.5)와 비슷하다 |
| 프롬프트 + 템플릿 | 프롬프트만 쓸 때보다 나아지는 점이 없다. **템플릿의 분홍 입술색이 환자 입술로 번진다** |
| 신원 유사도 | 템플릿을 쓰면 0.05~0.07 낮다. 얼굴 전체로 보면 같은 사람이며, 입술·치아 변화 때문이다 (아래 그림) |
| 속도 | 프롬프트만 1.7초, 템플릿 추가 2.6초 |

![템플릿 사용 시 신원 점수 하락이 큰 얼굴 (얼굴 전체)](assets/smile_v3_identity_full_worst.jpg)

## 5. 배포

상세: [docs/smile_tune/aws_deployment.md](../smile_tune/aws_deployment.md), API [docs/smile_tune/api.md](../smile_tune/api.md)

- Docker 이미지에는 코드만 들어간다. 모델·임베딩·얼굴 랜드마크 모델은 실행할 때 마운트하거나(로컬) S3에서 내려받는다(AWS).
- 필요한 리소스: klein-4B(약 7.9GB, 텍스트 인코더 없음), 텍스트 인코더의 tokenizer(16MB), `smile_final` 임베딩(약 0.4GB), `face_landmarker.task`.
- 테스트: 서버를 띄운 뒤 같은 사내망에서 `http://<서버 IP>:<포트>/docs`로 Swagger를 열어 바로 요청할 수 있다.

**배포 전에 처리할 것**

| 항목 | 상태 |
| --- | --- |
| `smile_final` 임베딩에 `patient_tooth` layout이 없음 (템플릿 요청 시 400) | 템플릿을 쓰지 않기로 하면 문서에 명시, 쓰려면 두 layout으로 재빌드 |
| 스타일 수정·삭제·빌드 API가 열려 있음 | 여러 사람이 쓰거나 외부에 열기 전에 읽기 전용 옵션 필요 |
| 다른 도메인의 웹 프론트엔드에서 호출 | 허용 출처를 지정한 CORS 설정 필요 (데스크톱 앱·서버 간 호출은 불필요) |
| `docker/design-tune-server/requirements.txt`가 git에 없던 문제 | `.gitignore` 예외 추가함, 커밋 필요 |

## 6. 한계와 다음 단계

1. **실제 환자 사진 검증**: 3·4절의 112명은 모두 합성 이미지이고 웃는 얼굴이다. 실제 환자 사진과 무표정 얼굴로 다시 확인해야 한다.
2. **여러 항목 조합 방식 교체** (상세: [embedding_modes.md](embedding_modes.md)): 지금은 여러 항목을 함께 바꿀 때 임베딩을 더한다(`delta`).
   측정해 보니 **4축 조합에서 고개 회전이 완전히 사라졌다**(정답 20.2° → delta 0.8°). 강도를 올리면 오히려 더 줄어든다.
   원인은 임베딩이 512개 토큰의 나열이고, 문장 길이가 바뀌면 뒤 토큰이 밀려 변위끼리 겹치기 때문이다.
   **조합된 문장을 그대로 인코딩하는 방식**(조합 preset을 미리 빌드하거나 서버에서 즉석 인코딩)으로 바꾸는 것을 권장한다.
3. **웃는 정도 75/100 개선**: 문장 강화, 턱을 포함하는 마스크, 또는 선택지를 "입 다물기 / 유지 / 크게 웃기"로 줄이는 방안.
4. **`natural` 결과의 아티팩트**: 변화가 없어야 하는 요청에서 치아에 얼룩이 생기는 사례가 있다.
